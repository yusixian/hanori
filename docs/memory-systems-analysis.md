# Bot 记忆系统全景分析 & cos-tool-bot 进化路径

> 调研时间：2026-03
> 调研范围：Memoh、Bub、OpenClaw、Letta/MemGPT、Zep/Graphiti、ChatGPT/Claude、MemOS、Alma、Kapy

---

## Part 1: 各方案核心总结

### 1.1 按设计哲学分类

#### 「自动提取派」— 系统决定记什么

| 方案               | 核心机制                                | 优点                                    | 缺点                             |
| ------------------ | --------------------------------------- | --------------------------------------- | -------------------------------- |
| **Memoh**          | 每轮对话→LLM 提取知识→向量 DB，语义检索 | 零配置个性化，per-member 隔离（容器级） | 提取质量依赖 LLM，有损压缩不可逆 |
| **ChatGPT Memory** | 自动预加载用户画像到每次对话            | 零配置即个性化                          | 黑箱，用户难以控制               |
| **Mem0**           | user_id/agent_id 维度的 embedding 记忆  | API 简洁，多维度隔离                    | 语义搜索噪声，过度提取           |

#### 「Agent 自管理派」— Agent 决定记什么

| 方案             | 核心机制                                               | 优点                     | 缺点                             |
| ---------------- | ------------------------------------------------------ | ------------------------ | -------------------------------- |
| **Letta/MemGPT** | OS 虚拟内存隐喻：Core(RAM)/Recall(磁盘)/Archival(归档) | Agent 自主读写，最灵活   | 复杂度高，需要精心调教           |
| **Alma**         | 文件系统 people profiles + CLI 命令读写                | 透明可控，结构化人物档案 | 无语义搜索，纯关键词             |
| **Kapy**         | 双模式：固定注入(宽泛概览) + 自主查询(精确检索)        | 哲学最清晰，DAG 因果链   | 依赖文件系统，目前关键词检索为主 |

#### 「原始事实派」— 不压缩，按需查

| 方案              | 核心机制                              | 优点                                 | 缺点                           |
| ----------------- | ------------------------------------- | ------------------------------------ | ------------------------------ |
| **Bub**           | 无限只追加 Tape + Anchor/Handoff 机制 | 零信息损失，Agent 自主管理上下文装配 | 需要强大的检索能力，多人不隔离 |
| **Claude Memory** | 默认空白，需要时工具调用搜索原始对话  | 透明可控，无幻觉注入                 | 冷启动慢                       |

#### 「知识图谱派」— 结构化关系网络

| 方案             | 核心机制                                   | 优点                           | 缺点                   |
| ---------------- | ------------------------------------------ | ------------------------------ | ---------------------- |
| **Zep/Graphiti** | 三层时序知识图谱(Episode→Entity→Community) | 处理知识更新最强(94.8% 准确率) | 基础设施重，维护成本高 |

#### 「文件即记忆派」— 朴素但透明

| 方案                     | 核心机制                                         | 优点                 | 缺点                           |
| ------------------------ | ------------------------------------------------ | -------------------- | ------------------------------ |
| **OpenClaw/Claude Code** | MEMORY.md 长期知识 + 日志文件，BM25+向量混合搜索 | 完全透明，用户可编辑 | 安全风险(注入攻击)，单用户设计 |

### 1.2 多角色处理方式对比

| 方案      | 策略                                     | 适合场景                         |
| --------- | ---------------------------------------- | -------------------------------- |
| **Memoh** | 显式容器级隔离 + per-member 记忆画像     | 需要严格隔离的多 bot 平台        |
| **Alma**  | per-person Markdown 档案，Agent 主动维护 | 社交型 Agent，需要深度了解每个人 |
| **Bub**   | 隐式包含：单条 tape，搜索时自然区分      | 信息不敏感的群聊场景             |
| **Mem0**  | user_id/agent_id 维度标记                | API 级多租户                     |
| **Zep**   | 图结构中实体节点天然区分                 | 需要理解人物关系的场景           |

### 1.3 Kapy 双模式理论（最值得关注）

Kapy 作者提出的「第一记忆模式 vs 第二记忆模式」是目前最清晰的理论框架：

- **第一记忆模式（固定注入）**：高级 API，参数少，强制/半强制调用
  - 目的：让 Agent 从零上下文搞明白「我是谁，在哪，要干什么」
  - 内容：宽泛的概览信息（compact summaries + 近期上下文）
  - 类比：人的「背景意识」— 你不需要主动回忆就知道自己是谁

- **第二记忆模式（自主查询）**：低级 API，高灵活性
  - 目的：Agent 已有明确目标，去找具体信息
  - 内容：精确的细节（原始日志、特定记忆、关键词搜索结果）
  - 类比：人的「主动回忆」— 你想起某件事然后去翻聊天记录

## Part 2: cos-tool-bot 当前记忆系统定位

### 2.1 现有系统架构

cos-tool-bot 已经实现了**三层记忆系统**：

| 层级               | 实现                                          | 表/存储                                          | 对应哪种模式                               |
| ------------------ | --------------------------------------------- | ------------------------------------------------ | ------------------------------------------ |
| **会话历史**       | per-chat 消息日志 + LLM 自动摘要              | `conversationMessages` + `conversationSummaries` | 第一记忆（注入）                           |
| **用户档案**       | per-user 结构化画像（traits/interests/notes） | `peopleProfiles`                                 | 第一记忆（自动注入）+ 第二记忆（工具查询） |
| **Bot 记忆**       | 通用/用户专属持久事实                         | `botMemories`                                    | 第一记忆（自动注入）+ 第二记忆（工具查询） |
| **群组上下文缓冲** | 内存 Ring Buffer（最近 N 条消息）             | 内存 Map                                         | 第一记忆（注入）                           |
| **情绪状态**       | 1 小时过期的内存 Map                          | 内存 Map                                         | 第一记忆（注入）                           |

### 2.2 在各方案中的位置

cos-tool-bot 的记忆系统最接近 **Alma + Kapy 的混合体**：

- 类似 Alma：有显式的 per-person 结构化档案（`peopleProfiles`）
- 类似 Kapy 第一模式：自动注入历史摘要 + 用户档案 + bot 记忆
- 类似 Kapy 第二模式：提供 `search_history`、`recall_memories`、`search_profiles` 工具
- 自动摘要压缩类似 MemGPT 的 Message Buffer 管理

### 2.3 当前系统已有的优势

1. **完善的触发与权限体系** — 群聊/私聊/管理员分层，per-group 覆盖配置
2. **丰富的工具生态** — 30+ 工具（Telegram 原生、Web、行为、记忆、Agent 代理）
3. **事件驱动续聊** — 投票/定时器/按钮回调触发 AI 响应
4. **自动摘要** — 超阈值时 LLM 压缩历史
5. **per-chat 并发锁** — 防止同一聊天并发生成

## Part 3: 进化建议

### 3.1 短期优化（当前架构内可做）

#### A. 强化「第一记忆模式」— 让 Agent 启动更快更准

**问题**：当前系统注入是平铺的（摘要 + 最近消息 + 档案 + 记忆），缺乏结构化的「情境感知」。

**建议**：

- 在 system prompt 构建时增加一个「情境摘要」层，不是简单拼接，而是根据当前对话特征（群聊/私聊、用户是否首次、是否有活跃话题）动态组装
- 参考 Kapy 的做法：把这个「情境组装」做成一个半强制的工具调用（或内部函数），在每个 turn 的第一步执行

**涉及文件**：

- `packages/bot/src/handlers/ai-reply.ts`（system prompt 构建逻辑）

#### B. 增强「第二记忆模式」— 给 Agent 更强的检索能力

**问题**：当前 `search_history` 和 `recall_memories` 是关键词匹配，缺乏语义理解。

**建议**：

- 为 `conversationMessages` 和 `botMemories` 添加 `pgvector` 向量字段
- 入库时通过 embedding 模型生成向量
- `search_history` / `recall_memories` 工具升级为混合搜索（关键词 + 语义）
- 参考 OpenClaw 的 BM25:向量 = 7:3 权重比

**涉及文件**：

- `packages/database/src/schema.ts`（新增向量字段）
- `packages/server/src/services/conversation-store.ts`（增强搜索逻辑）
- `packages/bot/src/tools/memory-tools.ts`（工具定义升级）

#### C. 记忆生命周期管理

**问题**：`botMemories` 只有增删，没有更新冲突检测。同一个事实可能被多次存储。

**建议**：

- 给 `botMemories` 增加 `category` 索引和去重逻辑
- Agent 存记忆前先搜索是否已有相同/矛盾信息
- 参考 Zep 的双时间戳模型：区分「事实有效时间」和「记录时间」，支持知识更新（"Alice 以前在 Google，现在去了 Meta"）

### 3.2 中期增强（需要架构调整）

#### D. 引入 DAG 因果链（Kapy 式）

**问题**：当前会话是线性的，跨聊天/跨 topic 的关联丢失。

**建议**：

- 为每个有意义的 turn 创建一个 `memoryNode`，包含 compact summary + 原始消息 ID 范围
- Agent 完成任务后上报「参考了哪些历史节点」，系统建立 DAG 连边
- 检索时可以沿因果链回溯，而不仅是按时间排序

#### E. Bub 式 Anchor/Handoff 机制

**问题**：群聊中多个话题并行时，线性历史混乱。

**建议**：

- 在群聊场景引入轻量级的 topic anchor
- Agent 可以标记「当前我在跟进 X 话题」，切换时 handoff
- 不需要完整的 Bub tape 架构，只需要在现有 Ring Buffer 上加一层 topic 标签

### 3.3 推荐优先级

cos-tool-bot 已经站在一个很好的位置。它的三层记忆（历史+档案+记忆）+ 工具驱动的架构，本质上已经实现了 Kapy 双模式的雏形。

推荐的优先级排序：

1. **最高价值**：B（语义搜索增强）— 这是第二记忆模式的关键瓶颈，pgvector 扩展成本低但收益最大
2. **次高价值**：A（情境感知注入优化）— 提升第一记忆模式的质量，改善 Agent 的"开局理解力"
3. **中等价值**：C（记忆去重与更新）— 防止记忆膨胀，保证长期使用的质量
4. **探索性**：D/E（DAG + Anchor）— 适合群聊活跃度高时再考虑

## Part 4: 要不要引入外部记忆框架？

**结论：不建议。** 原因：

1. cos-tool-bot 已有的记忆系统与项目架构深度集成（grammy + Hono + Drizzle），引入 Mem0/Zep 等外部框架反而增加依赖和复杂度
2. bot 已经有了完善的工具系统，「Agent 通过工具管理记忆」这条路已经走通
3. 上面建议的增强（向量搜索、情境感知、去重）都可以在现有架构上增量实现
4. 外部框架的多租户模型（Mem0 的 user_id/agent_id）不如当前的 botId+chatId+telegramId 贴合 Telegram bot 场景

**唯一值得借鉴引入的**：`pgvector` 扩展（用于向量搜索），这是基础设施层面的增强，不算框架依赖。

## 验证方式

如果决定实施上述建议，可以按以下方式验证：

1. **B（语义搜索）**：在现有 bot 上对比关键词搜索 vs 混合搜索的召回质量
2. **A（情境注入）**：对比优化前后 Agent 对历史话题的理解准确度
3. **C（去重）**：监控 `botMemories` 表的增长速率和重复条目比例
