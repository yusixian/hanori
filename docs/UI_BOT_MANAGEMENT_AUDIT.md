# Bot 列表与概览效率审计

状态：v0.7.0 已完成独立审查、本地验收、PR CI、合入和 GitHub Release。记录于 2026-09-22；基线为 v0.6.0 候选提交 `7c2673de6f5387562b0535c8f5ae49df29a2d99b`。发布目标为 `b49dcd5994851017cd87f7cd23397d6aec30482e`；PR #91，PR CI `35641125157` 成功。合入后 CI `35641965847` 已核实 completed/success；未部署生产。

## 主要发现

1. 列表请求失败被当成空列表。`pages/bots/list.tsx` 只读取 `useList` 的 `data/isLoading`，将错误后的缺失数据变成空数组；页面显示 0 个 Bot、0 个运行中，以及“添加第一个 Bot”。`dataProvider` 已经抛出失败，问题在页面的错误分支。详情页同样忽略 `useOne.isError`，将请求失败显示为未找到 Bot。
2. 列表固定读取第一页 100 项，没有分页，顶部数量使用当前数组长度。服务端返回 `total` 并限制 `limit <= 100`；第 101 个起无法通过列表访问。不能只过滤当前 100 项后把结果称为全量搜索。
3. 手机列表扫描成本偏高。8 个 Bot 的夹具中，390×844 首屏只能看到两张约 240px 高卡片；masked token、重复状态点与空白占据大量空间。概览没有 AI 设置、对话或日志入口，手机上仍需打开侧栏再选页面。

## 浏览器证据

主代理在本地生产预览 5192、1440×900 与 390×844 下拦截全部 API，使用 8 个虚构 Bot 验证列表、详情与 HTTP 500。失败确实呈现空数据引导，未显示错误或重试。页面无横向溢出，但手机卡片密度和概览路径仍有改进空间。

脚本：`.acceptance/ui-efficiency/verify-bot-management-baseline.mjs`。截图与可见内容记录：`.acceptance/ui-efficiency/bot-management-baseline/`。没有修改真实 Bot、调用生命周期操作或访问生产数据。

## 下一轮建议与边界

- 首先区分加载、错误、真实空数据与成功数据，提供就地重试；刷新失败时保留已有数据并明确标记状态。
- 使用真实 `total` 和分页，缩小卡片高度；名称、单一状态、运行时长与操作保留，masked token 仍可在详情读取。
- 概览加入适用于当前平台的少量常用链接，复用现有路由与权限边界。
- 已核实 Bot 列表 API 及 DataProvider 只支持 page/limit。本轮不添加名称搜索或状态筛选；全量搜索需作为后续 route/provider/UI 同步切片，不能只过滤当前页。
- 生命周期、删除确认和授权接口不是本次布局改进的附带重构范围；如发现实际副作用缺陷，先独立复现再确定修复。

## v0.7.0 审查补充

- 分页依赖的服务端查询此前没有排序；主代理添加创建时间升序与 ID 决胜项，并用真实 Drizzle SQL 生成路径检查不同页的排序和 offset。该修复提供确定顺序，不声称 offset 分页能冻结并发新增/删除时的数据快照。无需迁移或变更 API 字段。
- 切换到未缓存页面时会卸载分页焦点；要求只在用户主动换页并载入完成后回焦/滚动到列表标题，初次加载和后台刷新不抢焦点，并补延迟加载回归。
- 长 Bot 名称保留最多两行，初始错误增加 alert 语义。开发预览 React Grab 浮层会遮挡手机底部分页鼠标操作；预验收使用真实键盘路径，最终生产预览再检查鼠标/触屏路径。
