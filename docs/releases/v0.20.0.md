# v0.20.0 — 在聊天中诊断 Bot 运行情况

Bot 管理员可以直接询问“为什么上一条消息没有回复”，查看当前聊天的运行状态、有效配置、请求链路、近期错误和脱敏诊断事件。

## 新功能

- 新增五个只读 AI 诊断工具，区分排队、模型超时、工具失败、空回复与 Telegram 投递失败，支持查询上一条自己的消息。
- 查询限定当前 Bot 和当前聊天；身份来自真实 Telegram 消息，仅当前 Bot 管理员可用。输出采用白名单，不返回凭据、完整提示词或原始消息正文。
- 每次查询均写入审计，包括拒绝和未找到记录的情况。查询有频率、分页和响应大小限制；审计失败时不返回诊断数据。

## 修复

- 运行状态和有效配置工具不再暴露无用的筛选参数；链路、日志与错误查询兼容可选参数的 `null` 和空白 ID，避免空 `toolCallId` 导致 `invalid_request`。
- 五个工具同时调用时，超出四个审计写入槽位的查询进入有界等待队列，避免数据库正常时误报 `Diagnostic audit unavailable`。排队与写入仍共享一秒期限，超时的等待项不会继续写入。
- 稳定共享 CI runner 上涉及子进程的测试，减少并发资源竞争导致的偶发失败。

## 使用与升级

- 无数据库迁移，无新增环境变量或审计开关；沿用已有日志存储。保留现有环境变量、加密密钥和持久卷。
- 升级并重启服务后生效。请求链路保存在 Bot 当前运行实例的内存中，默认保留最近一小时，最多 500 条；旧版本或重启前的链路不会补录。
- 历史链路缺失会返回未找到或空结果，不影响运行状态和有效配置查询。正常使用不需要手动填写当前请求的 message ID、trace ID 或 tool call ID。
- 使用示例、权限和错误含义见公开文档「参考 → AI 运行诊断」（`/docs/reference/runtime-diagnostics`）。

## 验证边界

回归覆盖模型传入空 ID / `null`、五工具并发、审计排队与超时、槽位恢复、参数拒绝及聊天隔离；真实工具工厂与诊断服务的集成测试验证调用契约。发布前执行仓库检查、生产构建及公开文档的桌面和移动端浏览器验证。

线上只读日志确认了原始空参数问题和成功落库的审计记录；修复后的真实 Telegram / 模型调用仍需升级后验证。GitHub Release 发布不会自动更新运行中的服务或公开文档站。
