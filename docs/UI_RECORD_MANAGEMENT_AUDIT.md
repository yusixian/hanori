# 人物档案与记忆管理：下一轮基线

2026-09-22，在 v0.9.0 发布阶段完成有界调查。生产面板构建 + 全 API 模拟，1440×900 与 390×844；没有真实 Bot、模型、数据库读写。当前两页代码与 v0.8.0 相同。

## 浏览器已复现

| 操作             | 模拟响应                   | 两档均观察到的结果                                     | 下一轮验收                                             |
| ---------------- | -------------------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 初次打开人物档案 | GET profiles 返回 HTTP500  | 页面显示「未找到人物档案」，没有错误提示或重试         | 显示加载失败和重试，不误报为空；恢复后可显示记录       |
| 创建一条记忆     | POST memories 返回 HTTP500 | 创建表单关闭、草稿消失，没有错误提示，随后自动刷新列表 | 失败保留草稿和表单，明确错误，可再次提交；成功后才收起 |

证据：`.acceptance/ui-efficiency/record-management-baseline/` 中4张截图和 `evidence.json`；脚本 `verify-record-management.mjs`。主代理复核请求记录与截图；无页面运行错误，但不等于操作成功。临时5193预览已关闭。

## 当前源码候选，仍需补复现

- 人物保存/删除、记忆保存/删除也未完整检查 HTTP/application 失败；需要逐条确认状态及成功反馈，不据一条创建用例声称覆盖全部写入。
- 人物搜索请求带分页，但服务端搜索分支固定最多10条并使用返回长度作为total；需验证第11个匹配不可达的实际旅程。
- 记忆 API 支持 Telegram ID 筛选，现有面板只提供全部/通用；这是效率改进候选，不与故障恢复混作同一缺陷。

## 下一轮边界

优先修复已复现的列表失败与写入失败保稿，再覆盖相邻管理动作和请求切换。复用已有错误卡片、重试与陈旧结果提示模式；保留权限、Bot范围、中文/英文、桌面/手机。每项写入必须区分成功、失败和正在提交，验证失败后不丢草稿、不误删本地记录、不重复提交。查询分页与新增筛选另按证据决定版本范围。

尚未实施本轮修复，不作为 v0.9.0 已交付内容。后续继续从本基线和最新源码恢复，执行审查、文档、CI与发布闭环。
