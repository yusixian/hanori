## 当前源码候选，仍需补复现

- 调查时人物保存/删除、记忆保存/删除未完整检查 HTTP/application 失败；本轮已补各动作验证，结果见下方。
- 人物搜索请求带分页，但服务端搜索分支固定最多10条并使用返回长度作为total；需验证第11个匹配不可达的实际旅程。
- 记忆 API 支持 Telegram ID 筛选，现有面板只提供全部/通用；这是效率改进候选，不与故障恢复混作同一缺陷。

## 下一轮边界

## v0.9.1 实现与审查

基于 main `ce8a93c77925751d8b4939b6e26a72f366e9961f`。仅改管理界面的读取/写入状态、双语反馈与对应指南，没有修改服务端接口、权限、数据库或个人化规则。

- 列表检查 HTTP 与业务结果，初始错误不显示空列表/零总数；相同查询刷新失败保留已知结果，切换查询隐藏不属于新条件的旧数据。
- 创建/编辑/删除只有确认成功才收起表单或刷新；失败保稿并提供「刷新列表」。成功写入与随后刷新失败分别显示。
- Bot 使用 keyed 页面实例，列表带 AbortController 与过期响应保护；提交期间锁定相关操作，失败后的确认刷新也禁止重复提交。
- 独立 Sol 审查指出人物档案确认刷新中仍可重提、切 Bot 后绑定写入继续请求旧 Bot；主代理修复即时锁和卸载保护，增加慢 GET 与绑定 PUT 竞态回归。
- 整合后人物档案24项、记忆11项，共35项浏览器回归通过；Panel typecheck/生产构建、相关lint/format、i18n2329 keys通过。记忆确认刷新期间切筛选会中止核对的P2也已修复：搜索、两项筛选、清除和分页有禁用与同步guard，并补慢GET回归。修复后35项回归、类型/构建和两档生产夹具复验通过，独立窄复审无剩余P1/P2。

## 下一轮检索效率调查

Sol对当前源码只读追踪确认：Panel传page/limit/search，GET profiles搜索分支忽略分页，store.searchProfiles固定limit10且路由把返回长度当total，因此第11项以后的匹配不可达。这是代码路径证据，尚未增加真实数据库或浏览器边界复现。

建议保留供AI memory/tool callback使用的searchProfiles 10条语义，为管理侧listProfiles扩展可选search，统一rows/count筛选并加入lastSeen/id稳定排序。Panel复用现有Pagination。搜索通配符现有语义保持，是否改literal搜索另作明确决定。

验收应覆盖25个匹配档案的20+5两页、真实total、Bot隔离、原搜索字段、清空回第一页和请求切换；数据库测试不能以Panel模拟API代替。

记忆API现有telegramId可选字符串：general对应NULL，可转数字的字符串精确匹配，省略不过滤；非数字目前静默忽略。工作区viewer可读，写要求owner/admin/editor，列表保留Bot范围。面板仅有全部/通用，没有具体用户输入。下一版需决定明确的输入/URL状态、错误处理和紧凑桌面布局，避免用户输入无效ID却看到全部结果。
