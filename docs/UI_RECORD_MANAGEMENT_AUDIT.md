# 人物档案与记忆管理：基线与 v0.9.1 验收

2026-09-22，在 v0.9.0 发布阶段完成有界调查。生产面板构建 + 全 API 模拟，1440×900 与 390×844；没有真实 Bot、模型、数据库读写。调查时两页代码与 v0.8.0 相同。

## 浏览器已复现

| 操作             | 模拟响应                   | 两档均观察到的结果                                     | 下一轮验收                                             |
| ---------------- | -------------------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 初次打开人物档案 | GET profiles 返回 HTTP500  | 页面显示「未找到人物档案」，没有错误提示或重试         | 显示加载失败和重试，不误报为空；恢复后可显示记录       |

## 当前源码候选，仍需补复现

- 调查时人物保存/删除、记忆保存/删除未完整检查 HTTP/application 失败；本轮已补各动作验证，结果见下方。
- 人物搜索请求带分页，但服务端搜索分支固定最多10条并使用返回长度作为total；需验证第11个匹配不可达的实际旅程。
- 记忆 API 支持 Telegram ID 筛选，现有面板只提供全部/通用；这是效率改进候选，不与故障恢复混作同一缺陷。

## 下一轮边界

优先修复已复现的列表失败与写入失败保稿，再覆盖相邻管理动作和请求切换。复用已有错误卡片、重试与陈旧结果提示模式；保留权限、Bot范围、中文/英文、桌面/手机。每项写入必须区分成功、失败和正在提交，验证失败后不丢草稿、不误删本地记录、不重复提交。查询分页与新增筛选另按证据决定版本范围。

上述为 v0.9.0 结束时的基线，不作为 v0.9.0 已交付内容。修复进入独立的 v0.9.1，记录如下。

## v0.9.1 实现与审查

基于 main `ce8a93c77925751d8b4939b6e26a72f366e9961f`。仅改管理界面的读取/写入状态、双语反馈与对应指南，没有修改服务端接口、权限、数据库或个人化规则。

- 列表检查 HTTP 与业务结果，初始错误不显示空列表/零总数；相同查询刷新失败保留已知结果，切换查询隐藏不属于新条件的旧数据。
- 创建/编辑/删除只有确认成功才收起表单或刷新；失败保稿并提供「刷新列表」。成功写入与随后刷新失败分别显示。
- Bot 使用 keyed 页面实例，列表带 AbortController 与过期响应保护；提交期间锁定相关操作，失败后的确认刷新也禁止重复提交。
- 独立 Sol 审查指出人物档案确认刷新中仍可重提、切 Bot 后绑定写入继续请求旧 Bot；主代理修复即时锁和卸载保护，增加慢 GET 与绑定 PUT 竞态回归。
- 整合后人物档案24项、记忆11项，共35项浏览器回归通过；Panel typecheck/生产构建、相关lint/format、i18n2329 keys通过。记忆确认刷新期间切筛选会中止核对的P2也已修复：搜索、两项筛选、清除和分页有禁用与同步guard，并补慢GET回归。修复后35项回归、类型/构建和两档生产夹具复验通过，独立窄复审无剩余P1/P2。
- 1440×900、390×844生产夹具各36次模拟请求，覆盖两页完整CRUD错误、保稿、恢复与成功后刷新失败；无页面错误/横向溢出，主代理查看了实际截图。空列表创建成功后刷新失败，不再同时显示过时的0条/空文案。证据 `.acceptance/ui-efficiency/record-management-final/`，脚本 `verify-record-management-final.mjs`。
- 公共隐私/记忆指南与导航入口、v0.9.1 版本正文和导航同步；文档 typecheck/build、匿名访问/深链/搜索/版本导航的14项桌面手机检查通过。

不承诺离开页面或网页刷新后保留草稿。网络故障可能发生在服务端已经执行之后，因此提示“无法确认”并先核对列表，没有自动重放写入。人物搜索分页与记忆按具体ID筛选仍为后续候选。
