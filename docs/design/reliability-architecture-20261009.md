## 第八轮：IMAP 连接恢复与停止边界

本轮调查发现四个具体故障：首次快照失败提前标记初始化完成，后续会转发未被记录的历史邮件；SDK 的 `error` 事件无监听，可进入服务端退出处理；IDLE 故障可能返回 `false`，单纯 Promise catch 无法恢复；停止后的旧解析任务仍可能开始发送。

Astra 使用已安装 ImapFlow 源码和本地探针复核：未连接网络的真实 SDK 实例可通过 `emitError` 复现未处理事件；真实 IDLE command 在模拟 NoConnection 时返回 false，原监控没有启动恢复轮询；内存连接配合真实解析器复现停止后 sendCard 从 0 次变为 1 次。首次快照的新增行为测试也在修复前确认发生了历史邮件发送。

修复边界：运行周期身份与连接身份分别判断；旧连接不能关闭新连接或在停止后继续发起邮件转发；当前运行周期已经成功发送的结果仍需记入去重记录。已发出的 Webhook 无法撤回，不据此承诺远端取消或跨重启去重。

- IMAP 模块统一处理 error／close 与 IDLE false，单个连接失效仅启动一份轮询；正常 IDLE true／undefined 结果不触发恢复。
- 首次 UID 快照以临时集合收集，成功后才提交初始化状态；stop 同步失效运行周期，旧 fetch／parse／send／logout 和事件不能污染新周期。发送成功后的去重与连接是否仍有效分别判断，标记已读只操作捕获的有效连接。
- 定向回归 15 项通过；最初 5 项中 4 项失败，分别复现快照、error、IDLE false 和停止后发送问题。新增覆盖正常 IDLE、后续断线、停止期间连接、旧事件、标记已读失败和五次重试上限。

## 第九轮：IMAP 未读队列推进与协议命令顺序

只读探针确认：50 条历史未读、过滤不匹配或禁用事件前缀均可使 UID 51 永久停在原批次上限之后。历史场景 3 轮无解析／发送，过滤场景重复解析前 50 条共 150 次，禁用场景首轮解析后跳过；后面的新邮件始终未处理。

Astra 通过真实 SDK 原型的无网络探针确认另一个阻塞：流式 `fetch()` 在 yield 后等消费者继续才确认本条响应；消费者在循环内 await STORE，而 STORE 排在未完成的 FETCH 后，形成互相等待。LOGOUT 也可能被此状态阻塞。

采用一次 UID 搜索快照后顺序处理候选；每封 `fetchAll([uid])` 完整完成后再解析、发送及标记已读，正文内存只保留一封，代价是每封一次 IMAP 读取往返。UID 搜索列表仍为 O(未读数量)，与旧 SearchObject fetch 内部的完整 SEARCH 相同，不声称元数据扫描已分页或限制总条数。保留独占连接现有 mailbox lock，不为这一模块新增通用任务调度层。

SEARCH 的 false／undefined 不能作为成功空快照；处理中到来的 EXISTS 通知合并为当前周期结束后的补查。Astra 额外复现启动期间尚未注册 EXISTS 的窗口，监听应在初始 SEARCH 前安装。
