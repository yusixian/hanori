Hanori 数据库存放 Bot 配置、认证信息、消息、档案、记忆、日志、RSS、总结、生图记录和集成凭据。升级前务必先做好可恢复的备份，再动容器。

## 备份什么

至少保护三类数据：

1. PostgreSQL 数据库及迁移状态；
2. 挂载目录：图片、收到的文件、备份、编码工作区以及 app 数据目录下的固定版本插件制品；
3. `.env` 或部署平台 Secret 副本，特别是 `ENCRYPTION_KEY`、认证 secret 和外部集成凭据。

密钥必须与数据库分开保管：缺 `ENCRYPTION_KEY` 无法解密敏感配置，缺数据库无法恢复业务数据。

### 面板备份与 WebDAV 细节

- **权限与密码**：面板备份沿用 `DATABASE_URL`，通过临时密码文件传给 `pg_dump` 并在导出后清理（密码支持冒号和反斜杠，须为单行）。新建备份目录权限 `0700`，归档 `0600`；独立同步账号需确认读取权限。
- **导出与清理**：流式写入压缩归档，失败时终止进程并清理残余文件；远端上传失败仍保留本地有效备份并记录错误。保留策略清理失败只记告警、不影响本次备份状态，单条清理失败会记录备份 ID，其余符合条件的旧备份照常清理。
- **删除与下载**：删本地备份遇权限或文件系统错误时保留记录且不删远端（本地文件已缺失则照常清记录）。取消下载会停止服务端读文件，之后可重下。
- **文件名与 WebDAV**：前缀支持中文和空格，禁止 `/`、`\`、控制字符及路径穿越（空前缀用默认值）；不安全前缀需先修改再备份，异常历史文件名会被拒绝下载或删除。WebDAV 记录只展示 origin 和路径，上传失败仅记 HTTP 状态码；文件名作为单个路径段编码，保留目录与查询参数（旧版含 `#`、`?`、`%` 的对象需手动核对远端路径）。

### Bot JSON 导出与完整备份的区别

Bot JSON 导出/导入会剥离模型服务商、互动配置及插件中的 API Key、Cookie、Token 等密文，也不包含临时转录任务和结果；导入后插件默认停用，需重填凭据并手动启用。它不能替代数据库与密钥的完整备份。

完整 PostgreSQL 备份含加密插件配置和 24 小时内的转录正文，应按敏感数据保护。音频转换用的 `mediajobs`、`mediacontrol` 临时卷无需备份。恢复数据库后，下载或转换阶段中断的任务可有限恢复，已提交外部供应商转录的任务不会自动重发，请先核对账单。

## 升级前清单

- 记录当前版本（commit 或镜像 digest）及最近一次 ready 状态；
- 在维护窗口备份数据库，并验证归档可读；
- 确认目标版本迁移文件齐全且未改写已部署迁移；
- 核对 `COMPOSE_PROFILES` 及各自的 worker secret，避免意外启停 coding / media worker；
- 提前告知群成员维护窗口。

## 将历史加密密钥迁入显式配置

当前版本强制要求非空 `ENCRYPTION_KEY`。旧实例升级前，先核实线上实际运行的完整 commit 和生效环境变量（注意部署平台 Secret 和 Compose 变量会覆盖 `.env`）。

若旧实例未显式配置密钥，可在保留旧 Git 历史的私有仓库中离线生成升级配置：

```bash
node scripts/preserve-upgrade-env.mjs \
  --legacy-ref <已核实的旧部署完整40位commit> \
  --input /受保护目录/当前.env \
  --output /受保护目录/升级.env
```

- 工具优先保留输入文件中的非空密钥，仅在缺失或为空时从指定 commit 读取历史默认值。不联网、不连库、不改原文件，输出文件以 `0600` 权限独占创建（已有文件、符号链接或重复关键项直接拒绝）。
- 密钥以单引号保存以防 Compose 展开 `$` 或截断 `#`；若原密钥含单引号等无法无损表示的字符，工具会拒绝输出，此时须通过平台 Secret 保留原值，切勿换成新随机值。
- 此操作仅用于保住旧密文可读，不是密钥轮换；若历史密钥已泄露，需另行安排密文重加密。
- 如需一并恢复旧版硬编码在源码中的图片 MCP 地址，可在末尾追加 `--restore-image-mcp`（保留已有 `PIXAI_MCP_URL`，不迁移 OAuth token，部署后需 owner 重授权）。

## 执行升级

拉取目标版本后重建并启动数据库与 app，应用启动时会自动执行未应用的 Drizzle 迁移，随后启动 BotPool 和可选 worker。

使用 Git 克隆且数据库已运行的直接 Compose 部署，可按已审查的 release tag 升级：

```bash
./scripts/update-production.sh --version vX.Y.Z
```

- 脚本从 `DEPLOY_REMOTE`（默认 `origin`）解析 tag 对应 commit，先验数据库备份再切到 detached HEAD 构建并等待 `/api/health/ready`。仅允许向前升级，不自动降级；重部署同版本可加 `--force`。
- 维护者仍可在 `main` 上执行无参命令，但生产实例建议锁定发布 tag。备份目录由 `DEPLOY_BACKUP_DIR`（兼容旧变量 `COS_BOT_BACKUP_DIR`）指定，Compose 项目名由 `DEPLOY_PROJECT_NAME`（默认 `cos-bot-prod`）指定；这两个变量不从 `.env` 读取，需显式传入进程环境。

### 更换产品名、源码仓库或基础镜像

- **图片 MCP 旧版升级**：先等在途生图完成，在受保护配置中显式设置 `PIXAI_MCP_URL` 并重建，随后由 owner 重新授权（未设置则关闭图片 MCP）。
- **品牌与存储兼容**：更名或换仓库目录无需数据库迁移，务必沿用原有的 Compose 项目名（否则会新建空 volume）、数据库名、volume、认证组织标识和稳定密钥。`@cos-tool-bot/*`、`cos_tool_bot`、`cos-bot-prod`、组织 slug、本地存储 key 及默认备份前缀均保持兼容；旧 OAuth 客户端无需重注册。
- **跨无共同历史的仓库**：不要用 `git pull` 或强推切换私有库与独立公开库。在新目录拉源码、带入原配置并备份后，停旧 app 再以原 Compose 项目名启动新 app，防止同 Bot 被双实例轮询。Dokploy 新建应用会换资源名，需按平台流程迁走全部 volume。
- **源码归档**：归档无 `.git`，构建前手动设置 `APP_VERSION` 为对应 release 的完整 Git SHA（健康接口返回 SHA 而非 SemVer），走手动 Compose 更新。
- **升级到 pgvector 镜像**：先确认 PostgreSQL 大版本与 volume 兼容，再由应用创建 `vector` 扩展、列和索引；历史 embedding 可后续回填（未回填数据仍支持关键词搜索）。

## 升级后验证

按顺序检查：

1. `docker compose ps` 中 app、db 与启用的 worker 均正常；
2. `/api/health` 与 `/api/health/ready` 返回成功及预期版本 SHA；
3. 面板登录正常，Bot 列表与设置可读写；
4. Telegram `/help`、一次普通 AI 回复和 `/status` 正常；
5. 最新迁移已应用，备份页能看到历史记录；
6. 确认核心稳定后，再测图片、RSS、MCP、GitHub 等可选集成。

## 失败和回滚

构建失败、迁移失败或 ready 超时时，先保留日志和当前数据库。回退到上一镜像或 commit 后，若迁移已改过 schema，必须走向前修复或用已验证的数据库备份恢复，切勿手工删迁移记录。回滚后复查认证、Bot Token 解密、Telegram 收发和外部集成。

## 隔离恢复演练

在测试机执行 `node scripts/smoke-deployment.mjs`，会在独立的 app、数据库和 volume 中用合成账号和停用 Bot 检验恢复后的登录、凭据解密与文件完整性（不碰生产备份）。

加 `--previous-sha <上一支持版本的完整 Git SHA>` 可一并验证跨版本升级。恢复时务必使用原 `ENCRYPTION_KEY`，错密钥会导致凭据无法解密。详见[隔离部署检查](/docs/self-hosting/docker#隔离部署检查)。
