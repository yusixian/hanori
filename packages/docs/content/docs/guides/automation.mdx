这几类功能都涉及“之后自动做事”，但数据来源和权限不同：RSS 关注外部订阅源，群总结读取 Telegram 历史，定时器则在未来某个时间触发 Bot 行为。分别配置、分别验证，排错会更清晰。

## RSS 集合

正常关停会停止 RSS 调度和新的抓取／摘要操作，等待已开始的抓取、摘要投递及检查点写入后，再关闭其工具和数据库依赖。已接纳的抓取批次会继续完成剩余 Feed，关停时间可能跨多个抓取批次。抓取结束、超时或 HTTP 错误时会终止遗留请求，重定向中的旧响应也会释放。

同批到期集合会分别检查和触发；一个集合失败会记录其 ID，并继续处理其他集合，不会在同一批次立即重试失败项。原有摘要时间和冷却规则保持不变。

在 Bot 的 RSS 页面创建一个集合，然后添加一个或多个合法的 Feed URL。集合可以设置名称、描述、摘要提示词、摘要时间和最多纳入摘要的条目数；每个 Feed 也可以单独设置标题和条目上限。

推荐流程：

1. 先添加一个公开、稳定的 RSS/Atom 源。
2. 手动抓取一次，确认源能返回标题、链接和发布时间。
3. 在 Telegram 中让 Bot 列出集合或阅读未读条目。
4. 再启用定时摘要，观察一次实际投递。

Feed URL 和条目标题会进入工具调用与摘要流程。对于包含私密查询参数的地址，先确认日志脱敏和外部模型边界；不要把带 Token 的订阅链接贴在公开聊天中。

## 群聊总结

面板可以按群配置总结是否启用、执行时间、时区、窗口小时数、最多消息数、冷却和访问模式。访问模式可以允许所有成员，也可以只允许管理员手动触发或阅读。

### 范围、预览与覆盖信息

`/summary` 和聊天工具 `summarize_chat` 只读取当前 Bot、聊天及明确的话题；未在话题中调用时，仅读取带有明确主话题标记的记录，不汇总整个论坛。缺少话题标记的旧记录不会猜测归属。用户与上下文消息按作者当前隐私设置过滤，优先读取原始正文；没有单独原始正文的旧记录沿用已保存正文。普通总结保留所配置的角色过滤；Bot 回复只有能通过 `turnOrderId` 关联到同一 Bot、聊天和话题中、当前允许读取的来源发言时才会纳入。无法验证来源的旧回复、系统与工具记录不参与。

总结沿用独立总结模型、逐群 Provider/模型覆盖、提示词、执行记录及用量统计。服务端按 24,000 token 输入预算分块，长单条正文继续拆分而非只保留前 2,000 字；中间摘要归并后返回结果，不把整批历史塞回聊天 Agent。无法收敛的异常模型输出会明确失败。取消聊天或任务时，嵌套总结模型也会收到取消信号。

站点所有者可在 Bot 的 **群聊总结 → 预览总结（不发送）** 中指定聊天、话题、起止时间和最多条数，选择只使用原始发言，并填写本次要求。本次格式、篇幅与语气要求优先于默认输出约定，但不能改变数据范围与覆盖事实；模型输出仍需核对，不能把提示词中的字数要求当成硬性截断。预览不需要创建逐群配置，不发送 Telegram 消息，不改变手动总结冷却；仍使用总结开关、独立模型和消息上限，生成总结记录并计入用量。少于 5 条可用消息会返回“消息太少”及覆盖信息，不调用模型。

覆盖信息 `coverage` 的含义：

- `scope` 是实际查询的 Bot、聊天、话题、时间窗口和数量上限，`returnedCount` 是过滤后读取条数。
- `firstMessageAt` / `lastMessageAt` 是本次选中记录的实际时间；空窗口为 `null`。
- `complete=true` 表示这个范围内当前允许读取的数据库记录已读完；恰好达到数量上限不一定截断，服务会多查一条验证。
- 只有 `truncated=true`、`reason=message_limit` 才表示有更多符合条件的记录因数量上限未读入。
- `collectionCoverage=unknown` 表示无法证明 Bot 采集和保留了 Telegram 的全部历史，不能据此声称存在已知缺口。

所有者 API 为 `POST /api/bots/:botId/summary/preview`，请求包含 `chatId`、可选 `threadId`、带时区的 `since` / `until`、`maxMessages`，以及可选 `instructions`、`sourceRoles: "original"`。窗口最多 72 小时，最多 2,000 条且仍受总结配置上限限制。它始终不发送，只返回结构化摘要和覆盖信息；不能传入用户或管理员身份字段。

### 全局定时总结

在 Bot 的 AI 设置中启用总结，同时填写全局小时和分钟后，没有单独总结配置的群会使用该时间。使用总结设置中的时区，未填写时为 `Asia/Shanghai`。只有 Bot 正在运行、仍在群内、未迁移的已知群聊或超级群才参与；私聊、频道和类型未知的聊天不会自动收到总结。

群内最近 24 小时至少有 5 条符合所选角色过滤的已保存消息，才会进入全局调度。实际总结使用 Bot 的默认窗口、模型、消息数量和提示词设置；角色过滤不包含系统或工具消息。任意逐群配置都优先于全局设置，包括关闭状态，以及未设置定时时间的配置。删除逐群配置后，该群恢复全局规则。

全局执行权保存在数据库中，23 小时内不会重复申请；多个实例或服务重启也沿用该记录。生成或发送失败仍保留本次冷却，不自动重试或补发；服务停机错过的时刻也不补发。新关闭设置不会撤回已经接纳的任务。

**升级提示：此前保存但未生效的全局时间，在升级到包含此功能的版本后会开始触发。升级前请核对总结开关、小时、分钟和时区；不希望自动发送时，请关闭总结或清空全局时间。**

定时总结按聊天分别处理。某个聊天的配置读取或执行出错，会记录该聊天的错误并继续处理同批其他聊天；已登记执行时间的失败任务仍保留原有冷却，不会因此自动重试或补发。

正常关停会停止新的手动和定时总结，等待已经开始的模型调用与发送后，再关闭相关依赖。Telegram `/summary` 的成功回复也纳入等待，保留对原消息的回复方式。尚未开始申请执行权的定时任务不会因此消耗冷却；已经申请执行权的任务继续按原有结果和冷却规则收尾。暂停调度后仍可恢复，正常关停则关闭该服务实例。

手动命令：

```text
/summary
/summary 6h
/summary 200
/summary today
/summary yesterday
```

限制是单次最多 72 小时或 2,000 条消息。总结失败时，先区分消息太少、没有 Provider、命中冷却、权限不足和模型错误；这些原因需要不同的处理方式。

## 持久定时任务

群友可以直接提出“每月一日上午九点总结这个话题，发到本群”等需求。Bot 将内容、数据范围、发送位置、时区、首次执行时间、周期和执行 Agent 整理成计划卡；必要信息不足时先追问。配置对话开启后，后续补充在 10 分钟内不受普通接话冷却阻断，仍遵守隐私、停止和聊天排队规则。

任何成员都能提出计划，批准、试跑和取消提案需要 Bot 管理员或已配置的群代理管理员。群代理管理员不能批准发送到其他聊天的计划，跨聊天目标需要 Bot 管理员批准。Telegram 群管理员身份本身不等于已获 Bot 的代理授权。

- **确认创建/变更**：批准卡片上的版本；修改已有任务也必须重新确认，等待确认期间原计划继续生效。
- **试跑一次**：按待确认计划执行一次，保留执行记录，不自动启用周期任务，也不替代正式批准。
- **修改计划**：回复卡片说明变更，Bot 生成新版本；旧卡、过期卡和重复确认不能再次生效。
- **取消提案**：取消待确认版本。暂停或取消已经生效的任务，使用聊天管理工具或管理面板。

计划卡有效期为 24 小时。卡片展示发起人、源聊天/话题、读取窗口、目标、周期、时区、Agent 覆盖项和下次执行时间。源话题只读取记录中明确属于该话题的消息；旧历史缺少话题标记时不会猜测归属。只有查询确认数量上限截断时才说明这一限制；未知采集覆盖不当作已知缺口，不能把未读取的数据当作已经总结。

### 周期与时区

支持一次性时间、固定秒数间隔，以及按指定时区的每周、每月、每季日历计划；没有一天或七天的远期上限。固定间隔以经过时间计算；日历周期以当地日期和时间计算，一个月不等于 30 天，每季以起始月份为锚点每隔三个月执行。

月末日期不存在时取该月最后一天，例如每月 31 日在二月落到二月最后一天。夏令时导致当地时间不存在时，顺延到第一个有效分钟；当地时间重复时，选择第一次出现的时间。计划卡中的时区和首次时间应在批准前核对。

### 单独配置执行 Agent

定时任务使用独立的任务 Agent 默认配置，并可选择已有子代理名称，复用其模型、提示词、工具和执行限制。计划也可覆盖服务商、模型、提示词、工具列表、超时和最大步数。未覆盖的配置在执行时继承；卡片中的“继承”不表示把当时的默认值永久冻结。执行记录保留本次实际使用的配置。

任务执行不借用普通聊天的长对话记忆；只有计划明确授权的数据范围作为输入。暂停、恢复、取消和查询执行记录可通过聊天中的任务工具进行，也可在面板的定时任务页面操作。修改内容、时间或发送位置会形成待确认版本。

任务工具 `read_task_history` 返回已批准范围内的原始用户/上下文发言及覆盖信息；`summarize_task_history` 用同一固定窗口在服务端总结，遵循计划要求，只返回摘要和覆盖信息，不自行投递。来源与发送目标分开绑定，最大读取量不会超过批准值（最多 1,000 条），也不能通过工具参数扩大到其它聊天、话题或时间。最终投递仍由任务执行流程负责。

新的默认任务工具集包含 `summarize_task_history`；显式配置的工具白名单保持原样，若未列入该工具，需要修改计划并重新批准。已批准任务的总结使用任务自身的并发控制，不消耗或受普通 `/summary` 手动冷却阻断；总结关闭时仍会明确返回不可用。

### 从面板立即运行并观察

进入 Bot 的侧栏 **自动化 → 定时任务**，可直接查看这只 Bot 的计划；全局定时任务页仍可查看全部 Bot。已批准且未取消的任务可点击 **立即运行一次**，包括暂停中的周期任务和已完成的一次性任务。按钮运行当前已批准的内容，待批准修改不会混入本次执行。

手动运行会发送真实结果，但不改变周期、下次执行时间、暂停状态或周期失败计数。运行中按钮不可重复启动，服务器也拒绝同一任务的重叠执行；手动运行和周期执行共用此限制。待批准计划仍使用 **试跑一次** 和 **批准并启用** 两个独立操作。

任务卡显示下次执行、最近开始/结束时间、实际结果和错误。时间按计划时区显示并标明时区；页面每 3 秒刷新。展开 **执行记录** 查看手动/周期/试跑类型、计划及实际 Agent、输出、错误和记录到的 Telegram 消息 ID。请求已接纳或状态为“执行中”不表示成功；没有记录回执也不能凭一段输出认定投递成功。

### 模型协议兼容

任务模型沿用普通聊天的服务商与模型配置，并传入该模型的思考、温度和输出限制。服务商仍使用已配置的 API 地址；不会通过切换模型或关闭推理来掩盖错误。

当 OpenAI 兼容端点明确返回“Chat Completions 不支持 reasoning_effort 与 function tools，需使用 Responses”的 HTTP 400 时，仅把被拒绝的模型请求改为同服务商的 Responses 请求。已执行的工具不重放，后续模型步骤继续使用 Responses，并关闭服务端响应存储。其他参数错误、权限、限流或网络故障不会触发协议切换；Responses 失败会保留为失败记录。

默认思考模式保持默认；已有明确的 reasoning effort 可以保留，但供应商专属的 thinking 开关或 token 预算不能随意转换成 Responses effort。遇到不可映射的显式设置会报告错误，需管理员检查模型配置，不会静默删除推理设置。

### 恢复与失败

任务和执行记录存入数据库，重启后继续调度。停机错过多个周期时只补最近一期，不连续补发全部历史周期；同一任务不重叠执行。执行中进程退出的记录标为中断，因可能已经发送部分内容，不自动重放该次执行；后续周期按计划继续。

失败会记录错误。周期任务连续失败三次后自动暂停并通知；管理员检查原因后恢复。取消或暂停会停止后续调度并请求停止当前执行，但不能撤回已经发出的 Telegram 消息。试跑和手动运行不改变正式周期状态；手动执行中断后也不会消耗原来的下次周期。

### 旧定时器兼容

`set_timer` 在启用持久任务服务的实例中创建一次性**待审批计划**，不再绕过计划卡直接启动。`cancel_timer` 和 `/timers` 仍管理旧 AI 定时器及系统定时器，新任务使用任务管理工具或面板管理。

兼容旧服务时，`set_timer` 保留旧的到期继续对话行为，去除一天/七天上限；没有持久化服务的独立运行模式不接受超过 JavaScript 单次计时器范围的远期请求。已有旧定时器不会因升级自动转成新计划。

## 自动化上线检查

- 外部订阅源能在手动抓取中返回内容。
- 目标聊天允许 Bot 发送消息，必要时允许读取历史。
- 使用的 Provider、模型和时区已经明确。
- 访问模式和治理限制符合群成员预期。
- 能在面板日志或对应页面找到一次成功或失败记录。
- 关闭集合、总结或定时器后，新任务不再创建；已有运行中的任务按状态完成或失败。
