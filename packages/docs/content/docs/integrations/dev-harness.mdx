---
title: Dev Harness（预览）
description: 用一个专用 Bot 和 Telegram 话题群提 bug、跟进执行会话、调整交付配置，并在群里合并 GitHub PR。
---

Dev Harness 让一个专用 Bot 在 Telegram 话题群里接收 bug、交给你的执行机上的 Lody 会话修复，再汇报 PR 并提供一键合并。当前是预览阶段：已支持配置、项目话题、`/bug` 闭环、提醒与额度护栏、PR 卡片合并；大需求、发版与回滚尚未开放。

## 启用

1. 新建一个只用于 harness 的 Bot，在面板中添加；再建一个开启「话题」的私有超级群，把 Bot 设为管理员，并授予管理话题权限。
2. 参考仓库根目录的 `harness.example.yaml` 写一份配置，放在仓库之外，并用 `HARNESS_CONFIG_PATH` 指向它。未设置这个变量时 harness 完全关闭，其他 Bot 不受影响。
3. 必填项只有 `telegram.bot`（Bot 的 ID 或名称）、`telegram.chatId` 和 `telegram.owners`。项目可以写在 `projects` 里，也可以之后在面板中添加（见下文）。时长写作 `30s`、`45m`、`6h`、`7d`，百分比写作 `10%`。
4. 重启服务。配置有误时 harness 不启用，并在服务日志中列出出错的字段路径。

`topic: auto` 的项目会在首次启动时自动建一个话题并记住它，重启不会重复创建。

## 在面板或 Mini App 中添加项目

owner 打开网页面板的「Dev Harness」页，或在群里点 `/status`、`/harness` 回复下方的「⚙️ 管理项目」：

1. 从 GitHub App 能访问的仓库里选一个。列表包含 App 安装到的所有个人账号和组织；缺少的仓库点「授权更多仓库」去 GitHub 授权。
2. 选择执行机，按需修改项目名和 Lody 本地项目名。页面会显示仓库策略：有 `.cos/harness.yml` 时按文件，没有时按 `package.json`、Tuist、SwiftPM 等自动推断验证命令和项目类型。
3. 保存后立即生效：自动建项目话题并读取仓库策略，不需要 `/harness reload`。

面板中可以调整验证命令、规模闸门、发版片段要求和优先使用的 skill；风险分级与安全字段仍只能写在 YAML 里。`harness.yaml` 中的项目在面板里只读，与面板项目同名或同仓库时以 YAML 为准。

Bot 在 BotFather 中配置了主 Mini App 时，「⚙️ 管理项目」打开 Mini App；否则打开网页面板。

## 在面板中设置默认模型

「Dev Harness」页可以设置 lead 会话默认使用的 Lody 执行配置、模型和推理强度，也可以为单个项目（包括 YAML 项目）单独设置。面板设置高于 `harness.yaml`，低于 Telegram 的 `/harness set` 临时覆盖；留空的项继续使用 YAML 或内置默认。

- 内置默认是 Lody 中名为 `Codex` 的执行配置、`gpt-6-sol`、推理强度 `high`。
- 执行配置列表从 Lody 读取；模型可以从内置列表中选，也可以填自定义 ID。需要调整列表时在 YAML 中设置 `executors.lody.models`。
- 子会话跟随 lead 的厂商，审查换另一家：Codex lead 用 Claude Code 审查，Claude lead 用 Codex 审查。

## 在群里使用

只有 `owners` 中的用户、且只在配置的群里，命令和按钮才会生效。普通文字交给话题助手（见下文）；Bot 没有配置 AI 时只回复用法提示。

| 命令                                                   | 作用                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| `/bug <描述>`                                          | 在项目话题中提交 bug：建 issue、排队，并在空闲执行机上开 Lody 会话     |
| `/list`                                                | 项目话题中列出该项目进行中的请求；General 中按项目分组列出全部         |
| `/cancel [ID\|#编号]`                                  | 取消请求并停止 Lody 会话；话题中只有一个时可省略参数，多个时给出按钮   |
| `/retry [ID\|#编号]`                                   | 把「需要你看一下」且会话已结束的请求重新排队                           |
| `/status`                                              | General 中显示整体状态；项目话题中显示仓库、默认分支、执行机与排队     |
| `/quota`                                               | 按机器与 provider 显示 Lody 额度窗口；已过重置时间的窗口标为「已过期」 |
| `/new`                                                 | 清空当前话题的助手对话，从新对话开始                                   |
| `/harness config [路径]`                               | 显示生效值及其来源层                                                   |
| `/harness set <路径> <值> [--ttl 1d]`                  | 临时覆盖一个字段，可设到期时间                                         |
| `/harness unset <路径>` / `diff` / `export` / `reload` | 删除覆盖、查看差异、导出生效配置、重新读取 YAML                        |

在项目话题中执行时，配置命令只影响该项目。owner 列表、审批、风险规则、自动合并等级与凭据相关字段只能通过 YAML 修改。`reload` 失败时继续使用上一次的配置。

## 话题助手

在话题里直接发文字（不是命令，也不是回复卡片），Bot 会用它自己在面板里配置的 AI 回答。每个话题有独立的对话；项目话题只查询该项目，General 可以跨项目查询。

- 只读查询：GitHub 上的 issue、PR、评论、最近提交，默认分支上的文件与目录（单个文件最多返回 4 万字符，不读 `.env*` 与二进制文件），以及 Dev Harness 自己的请求、任务与事件。
- 总结话题里讨论过的需求；问「下一步做什么」时，先查 open issue、最近合并与 HANDOFF / 路线图文档，再给出按优先级排序的清单。
- 建议命令：回复下方附带「▶️ 执行建议」按钮，点击后按手动输入同一条命令执行（例如把讨论整理成 `/bug`），每条建议只能执行一次。助手自己不会建 issue、评论或合并。
- 对话里只保存你的文字和助手的回复；命令、卡片和命令的回复不会进入上下文。每个话题保留最近 200 条，30 天后删除；`/new` 立即清空当前话题。

回答期间会先显示「正在查…」，完成后原地替换为回答。开启 `telegram.chat.casualReplies` 时，普通消息仍交给通用 AI 回复，不经过话题助手。

## PR 卡片与合并

在 GitHub App 设置中启用 webhook：

```text
Payload URL: ${BETTER_AUTH_URL}/api/harness/github/webhook
Content type: application/json
Secret: 与 HARNESS_GITHUB_WEBHOOK_SECRET 相同
Events: Pull requests、Check runs、Check suites、Statuses、Pushes、Issues、Issue comments
```

GitHub App 还需要对目标仓库的 Contents、Pull requests 与 Issues 读写权限，以及 Checks 与 Commit statuses 读权限。未设置 secret 时，webhook 会拒绝所有请求。

配置中的仓库开 PR 后，对应项目话题会出现一张卡片：状态、风险等级、一句话摘要、CI 与缺失项。PR 更新时原地编辑同一张卡片。

- 默认只为 harness 分支（`harness/` 前缀）、`trustedAuthors` 中作者的同仓库 PR，以及带 `harness:track` 标签的 PR 生成卡片；来自 fork 的陌生 PR 不会出卡片。
- 风险等级按改动路径计算。`.cos/**`、`.github/workflows/**` 与 release-kit 配置的改动固定为 T3，只能在 GitHub 网页上合并。T2 点「合并」时卡片会就地展开改动文件和交付合同，再点「确认合并」；先点过「详情」的话一次就能合并。
- 合并前服务端会复核 head SHA 与 CI，再用 GitHub App 合并。新的 push 会让旧按钮失效。
- 按钮在重启后仍然有效，过期（默认 7 天）或已使用时会给出明确提示。每次按钮操作都会记入审计事件。

仓库可以在默认分支放一份 `.cos/harness.yml` 声明项目类型、风险路径和交付要求；只读取默认分支上的版本，PR 中的修改不会生效。

没有配置 CI 的仓库也可以添加：卡片显示「CI：未发现检查」，合并不会因为缺少检查被拦住。

## bug 闭环

`/bug` 创建带 `harness:bug` 标签的 issue，并在项目话题里发一张卡片；之后状态变化都原地编辑这张卡片。collaborator 给已有 issue 打上 `harness:bug` 标签，效果相同。

- 排队遵守 `guardrails.concurrency`：每台机器、每个项目的并发上限，以及同一代码分区同时只有一个写入者。会话没有声明分区前，按整个仓库计算。
- 额度达到 `guardrails.quota.pauseAt` 时暂停该 provider 的排队；配置了 `fallback` 时改用备用模型。本周额度达到 `warnAt` 时在 General 提醒一次。
- 会话开出 `harness/<请求 ID>` 分支的 PR 后，PR 卡片接替进行中卡片。CI 失败会把失败项发回会话，超过 `autoFixRounds` 轮后卡片标为「需要你看一下」。
- 回复卡片即反馈：内容写成 PR 评论、打上 `harness:revise`，再发给会话，卡片显示「修订中」。
- PR 卡片另有一行会话按钮：「打回」会弹出回复框，写下的原因按上一条的反馈流程发给会话；「取消」需再点「确认取消」，只停止会话、结束跟进，PR 保持打开，需要时在 GitHub 关闭；配置了 `executors.lody.sessionUrl` 时有「会话」链接；请求需要处理且会话已结束时出现「重新排队」。
- `/bug` 附带的截图以签名链接写进 issue：GitHub 能直接显示，执行机上的会话也能用 `curl` 下载。链接由服务端从 Telegram 实时取图，不含 Bot token，也不会提交到仓库；需要 `BETTER_AUTH_URL` 能从公网访问。拿到链接的人都能查看图片，与 issue 附件相同。非图片文件只列出 Telegram file id。
- 会话在 issue 上用 `Areas:`、`Question:`、`Needs spec:` 开头的评论与你沟通；问题会转到话题里，回复即作答。只有仓库 owner 和 `github.trustedAuthors` 中账号的评论会被当作协议，其他人的评论只是数据。
- 长时间无进展或总时长过长时只提醒，提醒上有 [继续等] [取消] [打开会话]；默认不会自动取消。

执行层通过 `lody-bridge` sidecar 调用 Lody：在 Compose 中启用 `harness` profile，设置 `LODY_CLI_TOKEN`（Lody 桌面端 Settings → Account → CLI Token）、两边相同的 `HARNESS_LODY_BRIDGE_SECRET`（至少 32 个字符），并给 app 设置 `HARNESS_LODY_BRIDGE_URL=http://lody-bridge:43190`。bridge 只执行 harness 需要的少数 `lody` 子命令，不发布端口。未配置时 `/bug` 仍会建 issue 并排队，卡片会说明执行层不可用；`/status` 会注明当前经 lody-bridge 还是本地 CLI。
