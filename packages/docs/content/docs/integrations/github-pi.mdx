GitHub 集成通过 GitHub App 安装授权把访问范围限定在选定仓库，再由服务端签发短期凭据，无需用户粘贴长期 Personal Access Token。

## GitHub App 配置

准备完整的一组 GitHub App 凭据：App ID、Client ID、Client Secret、私钥和 slug。五项必须全部填写或全部留空，缺项会导致启动或更新检查失败。

GitHub App 的三个地址均使用实例的公开 origin（将 `${BETTER_AUTH_URL}` 替换为实际地址）：

```text
Homepage: ${BETTER_AUTH_URL}
Setup:    ${BETTER_AUTH_URL}/api/github-app/setup
Callback: ${BETTER_AUTH_URL}/api/github-app/callback
```

私钥写入环境变量时使用带字面 `\n` 的单行 PEM，并收紧文件权限。安装流程不要开启绕过 Setup URL 的快捷 OAuth 选项，否则服务端无法获知所选 installation。

## 在面板中授权

owner 或 admin 在对应 Bot 的 AI/GitHub 入口发起授权，跳转 GitHub 选择安装范围和仓库，回调后返回面板。授权状态、仓库列表和撤销均以服务端为准；viewer/editor 无权访问该入口。

已连接的 Bot 在 GitHub 更改仓库范围或权限后，回到面板点击「同步授权仓库」，用有权访问该安装的 GitHub 账号完成授权。面板会刷新安装范围、该账号可访问的仓库和权限。Bot 管理员可直接使用同步列表中的全部仓库。现有 Bot 升级后也使用这份列表，旧的 Bot 白名单不再限制 GitHub App。

在 GitHub 选择「All repositories」可授权该账号的所有仓库，选择「Only select repositories」可逐个指定仓库。在面板断开连接会清理该 installation 的令牌与状态缓存（未完成的旧刷新无法回填缓存），下一次请求即失效，但已发出的 GitHub 操作不会撤销。

## Issue 创建确认

- **仓库定位**：管理员可让 Bot 调用 `github_list_repositories` 查看当前 Bot 的授权仓库（默认每页 50 条，支持 `page`/`limit`）。该工具不请求凭据、不访问 GitHub、仅管理员可用，返回 `accessVerified=false`，实际访问仍需过权限校验。遇到「自己的仓库」或 404（可能是私有仓无权访问）时，Bot 结合授权列表与上下文定位 `owner/repo`，仍有歧义则询问用户，失败结果带 `repository_resolution_failed` 便于日志追踪。
- **提案与有效期**：`github_create_issue` 先保存固定提案，再向发起管理员发送 Telegram 确认卡。默认**不过期**（跨 10 分钟或重启仍有效）；`githubToolsConfig.createIssueConfirmationTtlMinutes` 为 `null` 或未设时不过期，设为正安全整数时按分钟生效（仅影响新提案）。卡片会标注「不过期」或具体到期时间。
- **绑定与校验**：仅发起管理员可在原聊天（若在话题中则须在原话题）确认或撤销。普通群的回复串不算话题，回复不同消息不影响提案操作。每次点击都重新校验 Bot/工具启用状态、管理员身份、仓库授权范围和凭据。卡片绑定提案 ID、仓库、标题、完整正文和 SHA-256；修改内容需另建新提案并撤销旧提案。
- **撤销与查询**：点「撤销提案」或调用 `github_cancel_issue_proposal` 可取消待确认提案；调用 `github_pending_issue_proposals` 可查看当前会话中待确认、执行中及结果未知的提案，并重发最多 10 张卡片。已取消、过期或完成的旧按钮不可再执行。
- **防重与核实**：重复或并发点击最多触发一次创建。正文末尾会附带含提案 ID 和完整 hash 的 HTML 注释用于远端核实。
  - claim 后、发出请求前失败或中断：显示「未执行」，旧卡作废。
  - 进入发送阶段后遇网络异常、回执不明或服务重启：显示「结果未知」。点「核实已有 Issue」会用当前授权读取仓库（含已关闭 Issue，最多 10 页 × 100 条，限时 30 秒），标题、正文和标记完全匹配才记为成功；查不到或失败时保持「结果未知」，**不会自动重建**。
- **兼容与日志**：确认被拒时会区分账号、聊天和话题不匹配。旧版本生成的普通群确认卡若因旧回复串校验失败且状态为「待发起管理员确认」，可重新发起；「正在执行」或「结果未知」时应先核实再决定。回调日志只记提案 ID、点击账号、聊天、原始回复串、实际话题和状态，不记正文或凭据。
- **导出与其它操作**：Bot JSON 导出/导入不携带待确认提案；完整数据库备份按 owner/admin 权限保留持久化数据。push、丢弃 workspace、创建 PR、更新 Issue 等操作仍沿用 **10 分钟**确认与精确状态校验。

## 隔离 Pi coding worker

面板预填的 Git 提交署名为 `Hanori <hanori@example.invalid>`，可在 Bot 的 GitHub 工具设置中修改。

编码 worker 是可选 Compose profile，在独立网络和工作区中运行 Pi coding agent，不持有数据库凭据、GitHub App 私钥或推送权限。

启用时必须同时设置 `COMPOSE_PROFILES` 和 `CODING_WORKER_SECRET`。worker 与服务端通过内部 secret 认证，工作目录、Git 目录和出口代理由部署配置提供，任务受单次启动、超时、取消、干净工作区和精确状态确认约束。

GitHub 写入、push、创建 PR 和最终确认都在受信任的服务端完成。Bot 或 worker 汇报「已完成」不等于远端分支或 PR 已生效，管理员需在 GitHub 和面板复核。

## 常见失败

- **回调失败**：核对公开 origin、HTTPS、Setup/Callback URL 与 GitHub App 设置是否完全一致。
- **看不到仓库**：检查 installation 范围、App 权限和当前 Bot 绑定。
- **worker 不在线**：检查 Compose profile、worker secret、健康检查和出口代理；勿将 worker 暴露到公网。
- **worker 响应异常或中途断开**：任务记为失败且不自动重发；若 worker 已接单，后续任务需等待新启动的 worker 通过健康检查。连接断开不代表工作区未改动，请先检查工作区。
- **任务完成但无 PR**：将 worker 输出视为待确认状态，到 GitHub 核对分支与 PR。
