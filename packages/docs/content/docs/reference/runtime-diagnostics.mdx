title: AI 运行诊断
description: 管理员通过 5 个只读工具在聊天内查询当前聊天的运行状态、有效配置和请求链路。
---

当 Bot 还能回复时，Bot 管理员可以直接问：“为什么我上一条消息没有回复？请查询请求链路。”AI 会读取当前 Bot、当前聊天的诊断记录，定位请求停在哪一步。

若 Bot 已停机、模型持续不可用或 Telegram 无法投递，请改用管理面板和[故障排查](/docs/reference/troubleshooting)。

## 权限与范围

- **仅限当前 Bot 的管理员**：普通成员、纯 Telegram 群管理员和委派群管理员均无权调用。身份按实际发消息的 Telegram 用户校验，不能通过参数伪造用户、Bot 或聊天。
- **仅限当前聊天**：查别的群需去对应群发问。群内回复全员可见，注意场合。
- **强制审计**：每次查询（含拒绝、限流、无记录）都会记审计日志；审计写入失败时直接拒绝返回数据。

## 五个只读工具

| 工具                   | 用途                                                                      |
| ---------------------- | ------------------------------------------------------------------------- |
| `get_runtime_status`   | 查看运行状态、数据库连通性、当前聊天的排队、定时器、图片任务、RSS、配额。 |
| `get_effective_config` | 查看当前聊天实际生效的模型、超时、功能开关和可用工具。                    |
| `get_request_trace`    | 查自己上一条消息，或按 `traceId` 查同聊天内的请求阶段。                   |
| `query_sanitized_logs` | 按时间窗和条数查结构化脱敏诊断事件。                                      |
| `get_recent_errors`    | 按错误类别汇总近期错误次数。                                              |

这组工具只读，不改配置、不重启、不跑 shell。调用约束：

- `get_runtime_status` 和 `get_effective_config` 无需参数；其余三个可传 `traceId`、`messageId`、`toolCallId`（须来自真实记录，不知道就省略或传 `null`，空白字符串视为未传）以及 `windowMs`。
- `get_request_trace` 默认查自己上一条消息，传 `previous: false` 查当前诊断请求本身。
- 每页默认 **10** 条，最多 **50** 条，`offset` 最大 **500**，单次响应约 **24 KB** 上限。
- 频率限制：同一管理员在同一聊天 **10 次/分钟**，整个 Bot **60 次/分钟**。

## 判断请求卡在哪一步

请求链路按实际执行记录：入站 → 权限与触发判断 → 持久化 → 上下文构建 → 排队 → 模型 → 工具 → 回复生成 → Telegram 投递。未跑到的阶段不会补成成功。

- **排队中** ≠ 模型调用超时；**工具失败**后模型仍可能恢复并完成回复；**回复生成完成** ≠ Telegram 投递成功，需继续看投递阶段。
- 用户取消、未触发接话、命中配额、无可发内容各有独立状态；合并处理的消息需结合关联请求看，不要把缺少独立模型调用误判为丢消息。
- **生图任务**：工具事件关联 `generationId`、`providerOperationId` 和 `deliveryState`。即使链路已过期，仍可用 `/image status <任务 ID>` 查生成、取消、目标 chat/topic 和 Telegram 回执。查到 Skill 或预设不代表已提交生图。
- **组件状态**：`unknown` 表示缺少检查证据。`observationCapabilities` 会标明未接入能力（如模型/Telegram 主动探针为 `not_implemented / active_probe_not_configured`，GitHub 后台任务为 `not_implemented / task_reader_not_connected`），这代表能力边界而非故障；`lastModelEvent` / `lastDeliveryEvent` 仅反映最近一次实际观测。
- **工具参数与存储错误**：参数校验失败记为 `tool_invalid_input`；资产保存区分 `tool_not_found`、`tool_forbidden`、`tool_storage_error`（详情见面板 `AI tool input invalid` / `AI tool result` 日志）。存储结果未知时先查资产，不要直接当成未写入。
- **运行状态指标**：`version` 为部署的完整 commit SHA（不可读时为 `unknown`）；图片统计近 1 小时更新及未结束任务；RSS 返回活跃集合数和最近摘要时间；配额仅含当前聊天与当前用户。不主动调付费模型或发测试消息，暂未接入 GitHub 后台任务、主机指标和跨重启历史。

## 字段白名单与隐私

工具只返回白名单结构化字段（阶段、状态、错误类别、时间、耗时、有界关联 ID），配置仅投影诊断所需项。消息正文、完整系统提示词、工具入参/出参正文、URL、文件路径、堆栈、Cookie、Authorization、API Key、Bot Token、数据库连接串和私钥均不会返回。

管理面板里的运行日志仍可能含脱敏后的有界消息和工具内容，外发前请按[隐私、历史与记忆](/docs/guides/privacy-memory)复查。

## 保留窗口与常见状态

请求链路保存在当前 Bot 进程的内存中（响应中 `historyScope=current_process`）：

- 每个 Bot 最多保留 **500** 条链路，每条最多 **64** 个事件（保留最新）。
- 默认 **24 小时**无新事件即过期，可通过环境变量 `RUNTIME_DIAGNOSTIC_RETENTION_MS`（`1`–`86400000` ms，非法值回退默认）调整，重启生效。旧环境中若显式设过 `3600000`（1 小时），需修改或删除该变量才会生效新默认值。查询 `windowMs` 同样最长 24 小时，但不会延长实际保留期。
- 重启、过期或容量淘汰后，链路查询返回 `not_found`（运行状态与有效配置仍可查）；审计日志独立入库。
- 同一轮对话里重复加载未启用 Skill 或不存在的 Skill 参考资料，第 3 次失败返回 `skill_retry_limit` 并中止重试（详情记在 `AI tool result` 日志，新一轮重新计数）。
- `invalid_request` 表示参数非法；`Diagnostic audit unavailable` 表示审计写入超时或队列满（不一定代表数据库挂了），正常并发查询会短暂排队写审计。

常用问法示例：

```text
请查询我上一条消息的执行链路，说明最终停在哪一步。
请查看当前聊天的有效模型、超时和已启用工具，不要输出提示词。
请汇总最近一小时的错误，区分模型、工具和 Telegram 投递失败。
请检查当前聊天是否在排队，并说明哪些组件没有健康检查证据。
```
